# Concierge: Protocol-Native Support in Three Tiers

## What It Is

A knarr node that answers questions about the knarr protocol. Not a chatbot — a receipted, priced, three-tier service running entirely through the Thrall pipeline. No external APIs besides the LLM backend. No custom frontend code. Everything is config.

**Live right now:**
- `/s/ask/` — Free FAQ tier
- `/s/consult/` — Expert consultation (3 credits)
- `/s/support/` — Human review intake (8 credits)

Response time: ~3-5 seconds per query.

---

## Architecture

```
User visits storefront form (/s/ask/, /s/consult/, or /s/support/)
  │
  ├── Static HTML form (auto-generated by knarr expose system)
  │
  └── POST → cockpit → concierge skill
        │
        ├── tier = "faq" | "expert" | "intake"  (set by expose preset)
        │
        └── Thrall Pipeline ─────────────────────────────────────────
              │
              ├── 1. ENVELOPE: wrap user message as synthetic mail event
              │     from_node: "storefront"
              │     body_text: <user's question>
              │     trigger_type: on_mail
              │
              ├── 2. FILTER: rate limiting (10-20 req/min), no trust bypass
              │
              ├── 3. EVALUATE: LLM inference against tier-specific prompt
              │     L0: compact FAQ prompt (~1800 chars)
              │     L1: full knowledge base prompt (~5000 chars)
              │     L2: intake collection prompt (~900 chars)
              │
              ├── 4. ACTION: always "log" (DB trace, no side effects)
              │     The answer lives in eval_result.reason
              │
              └── 5. JOURNAL: full audit trail in thrall.db
                    (who asked, what recipe, what the LLM said, timing)
```

One skill handler (`concierge.py`, 120 lines). Three skill registrations at three price points. Three expose blocks. The `tier` field routes to the correct recipe.

## The Three Tiers

### L0 — FAQ (free)

**Recipe:** `concierge-faq.toml`
**Prompt:** Compact, ~1800 chars. Core protocol facts, common gotchas, embedded FAQ answers.
**Model:** Any small/fast LLM works (even gemma3:1b on CPU).
**Actions:** `log` (answer directly), `compile` (too complex, escalate to L1), `drop` (spam).

The L0 prompt contains a condensed knowledge base — install instructions, skill registration format, credit system basics, config keys, common pitfalls. Enough to answer "how do I register a skill?" or "what ports do I need?" without hitting a large model.

### L1 — Expert (3 credits)

**Recipe:** `concierge-expert.toml`
**Prompt:** Full knowledge base, ~5000 chars. Protocol internals, bilateral credit mechanics, settlement/netting, mail encryption, execution flow, deployment guidance, complete config reference.
**Model:** Large context LLM (Kimi, Gemini Flash, qwen3:32b).
**Action:** Always `log`. Detailed answer in reason field.

The L1 prompt embeds everything: credit notes (debit/credit/zero), W3C Data Integrity receipts, X25519 mail encryption, SyncEngine circuit breaker, group policies, settlement thresholds, the full knarr.toml section reference. It's a 400-word expert response drawn from ~8 reference documents covering the entire protocol.

### L2 — Intake (8 credits)

**Recipe:** `concierge-intake.toml`
**Prompt:** Structured collection, ~900 chars. Does NOT answer the question.
**Model:** Any LLM.
**Action:** `log`. Confirms receipt, summarizes understanding, asks for missing details.

The L2 tier collects and packages. It acknowledges the request, asks clarifying questions (environment, config snippets, error messages), and tells the user a specialist will follow up within 24-48 hours. The full request is logged in the thrall journal for human review. The requester never knows who reviews it.

## What Makes This Different

**It's a recipe bundle, not a service.**

The concierge is not a node we host. It's a folder:

```
concierge/
├── prompts/     (3 TOML files)
├── recipes/     (3 TOML files)
└── rag/         (8 markdown docs)
```

Any node operator drops these files into their Thrall plugin directory, runs `touch thrall.reload`, and their node answers protocol questions. Their compute, their LLM, their node. The knowledge is the product.

**The training loop is built in.**

Every question goes through `thrall-inject` for dry-run testing. Wrong answer? Adjust the prompt, add to the knowledge base, add a hotwire pattern. Right answer? Pattern confirmed. `thrall-tune` shows stats on recipe activity and decision distribution. The journal is the audit trail.

**It's priced, not free.**

L0 is free (FAQ). L1 costs 3 credits. L2 costs 8 credits. Every answer is a skill execution with a receipt. The concierge is self-funding — it earns credits by answering questions.

**It's protocol-native.**

No external API gateway. No webhook. No cloud function. The user hits a storefront form served by the knarr cockpit. The form calls a skill. The skill runs through Thrall. The LLM answers. The receipt is written. Everything stays on-protocol.

## Example Exchange

**Question (L1 Expert):**
> How does the bilateral credit system work? What happens when I run out of credits with a peer?

**Response (4.4 seconds):**
> The bilateral credit system in Knarr is a decentralized ledger where each node maintains its own balance with each peer. When a node provides a skill, its balance with the consuming node increases, and when it consumes a skill, the balance decreases. Each node has three policy values: initial_credit, min_balance, and tit_for_tat. The initial_credit is the starting balance for new peers (default 3.0), min_balance is the minimum balance allowed before a node stops providing skills (default -10.0), and tit_for_tat requires reciprocal skill provision to earn credit. When a node runs out of credits with a peer, it stops being able to consume skills from that peer until the balance is restored. Automatic settlement occurs when utilization exceeds a soft threshold (80%), settling to a target (50%), with a minimum settlement of 10 credits. Credit notes are signed receipts for every execution.
